# V4 — Developer intelligence and connected apps

V4 combines the planned developer and integration releases on `feat/thryv-v4`.
It reuses account sessions, the typed tool registry, owned Actions, same-session
confirmations, Companion's durable replay ledger, explicit memory and Talk. There
are no proactive jobs, reminders, screen vision, installers or unrestricted terminal.

DeepSeek may propose a batch of tools. V4 validates the proposals and selects only the
first; the remaining proposals are discarded. The workflow replans after the observed
result, with the same permission checks on every step. No discarded call is executed
or reported as completed. Legacy desktop batches remain rejected.

## Authorized projects

Pair Companion as in V1. Authorize an owned project **on that computer**:

```bash
thryv-companion workspace-add /absolute/project/path
thryv-companion workspaces
thryv-companion command-add WORKSPACE_UUID --command-name tests --runner pytest --cwd backend
thryv-companion run
```

Settings → Authorized Workspaces shows synced paths, selection and revocation.
Selection also selects the paired device. Local grants live in Companion's private
state directory and are pinned to the root's canonical path/device/inode. The server
independently binds each grant to the authenticated account and device. Remote
revocation is synced back and cannot be silently undone by another sync. Reauthorize
locally to obtain a new grant after removal. `workspace-remove WORKSPACE_UUID` removes
the local grant; running Companion synchronizes that removal.

List/read/search/metadata are SAFE. A create/replace is CONFIRM, shows the proposed
file content and requires the current SHA-256 (empty only for exclusive creation).
Symlinks, traversal, hard links, devices/FIFOs, sensitive paths such as `.env`, `.git`,
credential stores/private keys and non-text/oversized files are rejected. Recognizable
inline credentials are redacted; files with redactions cannot be edited. File reads
are limited to 48 KB; listing/search uses depth, file and result limits. File deletion
is not exposed. Concurrent external editors should still be paused during an approved
replacement: a hash check is not a filesystem-wide transaction with other applications.

`workspace_open` confirms and opens the canonical selected project in the existing
isolated VS Code profile with extensions disabled. A mapped window must be observed;
process creation alone is not reported as success.

## Development commands and Git

Command profiles are authorized locally, not invented by the model. Fixed runners:
pytest, unittest, Ruff, mypy, Python build, npm test/lint/typecheck/build, Make
test/lint/build, Next-style npm dev, and Python's static HTTP server. The model can
list configured profiles and select one, but cannot supply an executable, shell
string, environment variables or arbitrary argument list. Configure single-shot test
scripts; a watch process reaches the timeout rather than being treated as a pass.
Pytest supports an explicitly validated relative file/node selector for focused reruns.

Every run is CONFIRM. Linux bubblewrap creates a disposable project snapshot with no
network or user home. Protected files are excluded; eligible project dependencies are
mounted read-only. Process/file/output/CPU limits and a 60-second execution deadline
apply. Results preserve exit code, bounded redacted output and verification status.
Build/test modifications remain in the snapshot; persistent source edits require the
separate confirmed file tool. No runtime dependency download or arbitrary Make target
is allowed. Missing dependencies, unsupported sandboxing or excessive project size
fail explicitly. This is not a replacement for a fully configured project environment.

Approved servers run in the same isolated network namespace. At most two can run;
only THRYV-owned process IDs can be stopped. Process inspection distinguishes configured
ports from observed listening ports. **These are not host preview ports.** Servers are
stopped on local revocation, expiry (15 minutes), Companion shutdown or explicit Stop.
They are user-started processes, not background autonomous jobs.

Git status/diff/latest-five-log/branch and fetching the existing GitHub origin are SAFE.
Staging explicit paths, committing and pushing one branch require CONFIRM and a current
review hash covering files, index and refs. Git runs with sanitized configuration,
disabled hooks/helpers/external diffs and no arbitrary remote, protocol, force flag,
reset, clean or branch deletion. Standalone `.git` directories are supported; linked
Git worktrees/submodules are not. Commit identity must be configured in the repository.
Protected staged paths or recognizable staged secrets are rejected.

Authenticated Git transport uses an **existing local SSH agent**, only after explicit
`workspace-add /path --allow-git-ssh` opt-in, an existing verified GitHub host key and
per-push confirmation. Only the fixed existing GitHub origin is permitted. No private
key file or OAuth token is passed to the model. GitHub OAuth API connections are
separate from this local Git transport. Without SSH-agent authorization, public HTTPS
fetch works; authenticated push is blocked. GitHub branch permissions still apply.

## OAuth and Connected Apps

Configure host credentials locally (never in chat or source control):

```dotenv
OAUTH_ORIGIN=http://localhost:8000
GITHUB_CLIENT_ID=...
GITHUB_CLIENT_SECRET=...
GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
```

Backend startup from `backend/` reads root `.env`, then `backend/.env` overrides.
Environment variables take precedence. The backend includes IANA timezone data, including aliases such as
`Asia/Calcutta`, so chat and Calendar do not depend on the host's timezone installation.
Production OAuth requires an exact HTTPS
origin. Register these callback URLs with the corresponding OAuth application:

```
OAUTH_ORIGIN/api/integrations/github/callback
OAUTH_ORIGIN/api/integrations/gmail/callback
OAUTH_ORIGIN/api/integrations/calendar/callback
OAUTH_ORIGIN/api/integrations/drive/callback
```

Each connection uses user/session/service-bound single-use hashed state, five-minute
expiry and PKCE S256. The code exchange and refresh occur server-side. Fernet envelopes
bind tokens to both owner and service under the existing server vault key, independently
of DeepSeek. Neither tokens nor OAuth client secrets enter model prompts, browser
storage, logs or Actions. Connection identity is displayed separately from THRYV identity.
Disconnect deletes local tokens and attempts provider revocation; failure is reported
with instructions to revoke in the provider account. Google revocation can affect the
other Google grants for the same app. Refresh uses a conditional update so it cannot
resurrect a disconnected/replaced connection. No passwords or browser automation.

| Service | Initial scopes and reads | Confirmed writes |
|---|---|---|
| GitHub | `repo`; accessible repos, repo metadata, issues/PRs, commits, branches, workflow runs/jobs, checks | Issue, comment, PR creation |
| Gmail | `gmail.readonly` + `userinfo.email`; query metadata and selected message/thread | Optional `gmail.send`; send/reply/forward one reviewed message |
| Calendar | `calendar.readonly` + `userinfo.email`; primary-calendar events and free/busy | Optional `calendar.events`; create/update/delete primary-calendar events |
| Drive | `drive.readonly` + `userinfo.email`; search metadata and selected content | None |

GitHub OAuth's `repo` scope is broad because it is needed for private repositories;
THRYV still enforces confirmation for writes. Google write scopes are opt-in separately.
Google may require app verification/test-user enrollment for these scopes; host OAuth
configuration alone is not a connected account. Public deployment is not part of V4.

Only fixed official API endpoints are used, with no redirects, environment proxies or
model-supplied service URLs. Responses are capped at 1 MB and selected model context is
further bounded/redacted. Gmail search reads at most five metadata results; messages
prefer plain text, otherwise a snippet; attachment downloading is not exposed. Calendar
ranges use explicit IANA timezones/offsets and at most 31 days; all-day end dates are
exclusive. Drive supports Google Docs text export and selected text/JSON/XML files;
PDFs, binary files, spreadsheets, attachments and arbitrary mutation are not exposed.
Provider pagination/results are bounded and do not imply an exhaustive account search.

Official API references: [GitHub OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps),
[Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server),
[Gmail](https://developers.google.com/workspace/gmail/api/reference/rest),
[Calendar](https://developers.google.com/workspace/calendar/api/v3/reference),
[Drive files](https://developers.google.com/workspace/drive/api/reference/rest/v3/files).

## Bounded orchestration, memory and voice

A V4 tool starts a user-requested workflow with at most eight child Actions, five
minutes, bounded context and a small admission limit. Every child is revalidated;
SAFE/CONFIRM/BLOCKED is always trusted code. Writes pause for the existing same-session
confirmation. Cancellation/session loss/provider disconnect stop subsequent work and
retain completed audit results. Ambiguous service writes are not automatically retried.
No edit is reported as verified until a real configured test finishes successfully.

Calendar + Gmail and GitHub + workspace sequences use this same loop. Files, terminal
output, issues/PR text, email, Drive and web content are untrusted observations, never
authorization. V4-derived history is excluded from later initial tool planning. Relevant
explicit memories may guide the current request; retrieved content is never autosaved.
Talk/VAD/STT uses the same endpoint, confirmations and results. TTS waits for the parent
workflow to finish. Wake remains the unchanged off-by-default Beta; no model tuning.

Migrations `a401_workspace` and `a402_integrations` are additive. Use the existing
`uv run --inexact alembic upgrade head` procedure. V4 acceptance and release checks are
recorded separately in the verification report; fixture coverage is not live-provider proof.
